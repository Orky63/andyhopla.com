Monitoring & FinOps

AWS Synthetic Monitoring & Cost Optimisation

Client: Next Foundry — “Client Zero”
AWS Services: Amazon CloudWatch Synthetics, CloudWatch, Amazon S3
Infrastructure: Terraform
Focus: Monitoring, Infrastructure as Code, FinOps, Cost Optimisation

The Challenge

How frequently should a business website test itself?

The answer should reflect the importance and usage of the service—not simply the default configuration of the monitoring platform.

Using Next Foundry as “Client Zero,” I wanted to implement automated monitoring that could independently confirm that the website was available and responding correctly.

The Solution

I deployed an Amazon CloudWatch Synthetics canary to perform automated homepage checks.

The monitoring infrastructure was created and managed through Terraform, keeping the configuration repeatable, version-controlled and consistent with the wider Next Foundry AWS environment.

Initially, the canary ran once every hour.

Technically, the solution worked exactly as intended.

However, AWS subsequently notified me that 88 of the 100 monthly free canary runs had already been consumed.

That prompted a review of whether the monitoring frequency was proportionate to the service being monitored.

The Review

Rather than simply accepting the original configuration, I assessed:

  • How quickly a website failure genuinely needed to be detected
  • Current traffic levels and business criticality
  • Successful and failed canary-run retention
  • S3 artifact retention
  • CloudWatch monitoring requirements
  • The expected cost once the free allowance was exceeded

An hourly schedule would generate approximately 720 synthetic checks per month.

For a high-volume transactional or revenue-critical service, that frequency—or considerably more frequent monitoring—could be entirely justified.

For the current Next Foundry website, however, 720 checks per month provided limited additional business value.

The Optimisation

I revised the Terraform configuration to reduce the canary frequency while retaining meaningful availability checks throughout the day.

The change was deployed through the existing GitHub Actions CI/CD workflow, maintaining the Infrastructure as Code approach rather than making an unmanaged console change.

The website remains automatically monitored, but the monitoring now reflects the actual operating requirements of the service.

The Outcome

The project reduced unnecessary synthetic monitoring activity while retaining useful availability assurance.

More importantly, it demonstrated a wider cloud engineering principle:

More monitoring is not automatically better monitoring.

Every test, log, metric and retained artifact should have a purpose. Otherwise, a technically sound control can increase cloud consumption and operational overhead without materially improving the customer outcome.

Cloud cost optimisation does not begin by removing useful controls.

It begins by making those controls proportionate to the service they protect.
